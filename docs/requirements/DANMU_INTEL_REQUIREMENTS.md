## 0. 术语表

| 术语 | 含义 |
|---|---|
| **弹幕** | 直播观众在直播间发送的公开文字消息及其发送时间。 |
| **直播间** | 某个平台上某位主播的公开直播页面。 |
| **一场比赛** | 两支队伍之间的一次对战，包含若干**小局**。 |
| **小局** | 一场比赛中的一个回合/一局（如「第 1 局」）。 |
| **节点** | 一场比赛中值得单独出情报的关键时刻。分三类：**赛前（BP 前后）**、**局中（小局进行中）**、**复盘（赛后）**。 |
| **BP** | 赛前的禁用与选用环节（游戏术语，本文沿用行业通用叫法）。 |
| **切片** | 按时间段从一场比赛的全部弹幕中截取出的片段（对应某个小局或某个节点）。 |
| **规则层** | 由确定性规则计算得出的事实与统计（比分、时间轴、数量、密度、排名等）。 |
| **情报报告** | 交付给读者的最终产物，按固定的分段结构组织（见 6.6）。 |
| **灰信号** | 弹幕中出现的、指向「比赛可能不正常」的讨论聚集现象。它**只是风险提示**，不构成任何指控（见 6.5）。 |
| **会员** | 付费后获得完整情报访问权的用户。 |
| **访客** | 未付费的访问者。 |
| **管理员** | 维护系统配置与数据源的人员。 |
| **节点进度** | 一场比赛当前已产出哪些节点、下一个节点是什么。 |

## 1. 产品目标与价值

### 1.1 一句话定位

把直播间的公开弹幕，在比赛进行的几分钟内，变成**结构化的、可读的、可回溯的赛场情报**，
并按「赛后免费、赛中付费」的方式提供给读者。

### 1.2 要解决的问题

1. 弹幕是**即时、海量、易失**的信息流；比赛结束后几乎无法回看，价值随直播结束而消失。
2. 观众想知道的不是「谁赢了」，而是「**怎么赢的、为什么崩的、接下来该盯什么**」——
   这些信息散落在弹幕的讨论里，没有人替他们整理。
3. 想为这些情报付费的人，**没有一个方便的、不需要注册乱七八糟账号的付钱方式**。

### 1.3 交付的价值

| 对象 | 价值 |
|---|---|
| 普通读者 | 免费看到赛后复盘，理解一场比赛到底发生了什么。 |
| 付费读者 | 在**比赛还在进行时**就拿到情报，包括当前局势解读与后续观察点。 |
| 运营者 | 一份可自动运行、成本可控、边际收益随订阅增长的业务。 |

### 1.4 成功的判定

- 一场比赛从结束/关键节点结束，到情报报告上线，**在承诺的时效内**完成（见 7.1）。
- 情报报告的**事实部分零错误**（数字、比分、时间与官方一致）。
- 付费用户能**自助完成付款并立即解锁**，全程无需人工干预。
- 单场情报的**可变成本**低到可以被订阅收入覆盖（见 7.2）。

## 2. 用户与角色

系统有且只有三种角色，权限互不重叠。

| 角色 | 如何获得 | 能看到什么 | 能做什么 |
|---|---|---|---|
| **访客** | 默认 | 已结束比赛的复盘报告；订阅介绍页 | 浏览、订阅登记（留联系方式） |
| **会员** | 完成一次性付款且未过期 | 访客的全部 + **进行中**比赛的情报报告 | 浏览完整情报 |
| **管理员** | 由运营方授予 | 全部 | 配置数据源、查看运营数据、处理异常（如付款已到账但未解锁） |

**硬性要求**

- 管理员专属的功能**只能**由管理员访问；页面与接口都不得对访客/会员开放。
- 系统**不要求**读者注册账号密码才能阅读免费内容。
- 系统**不收集**读者的钱包私钥、助记词或任何可动用其资产的信息（见 7.5）。

## 3. 使用场景

### 3.1 读者：看完比赛想知道发生了什么

1. 读者在比赛结束后打开站点 → 看到本场比赛的复盘报告（免费）。
2. 报告给出比分、逐局关键过程、双方表现、以及下一场可以留意什么。
3. 读者若想在看比赛**当时**就拿到这类信息 → 进入订阅页。

### 3.2 读者：付费后在比赛进行中获得情报

1. 读者打开订阅页 → 选择档位 → 得到一个**专属收款地址**与应付金额。
2. 读者转账 → 系统自动确认到账 → 读者立即获得访问权（无需人工审核）。
3. 系统持续在比赛进行中更新节点情报；会员能实时看到最新节点。

### 3.3 会员：到期后的处理

1. 会员有效期将满 → 系统提前提醒。
2. 到期后 → 访问权限降级为访客（仍可看赛后复盘），并有**短暂宽限**避免误伤。

### 3.4 管理员：新增一台直播源

1. 管理员进入后台 → 添加一场比赛 / 一个直播间（平台、地址、所属联赛）。
2. 系统在**一分钟内**生效，无需重启服务。
3. 比赛开始后，采集自动开始；比赛结束自动停止。

### 3.5 管理员：处理付款异常

1. 会员反馈「已付款但未解锁」。
2. 管理员凭**交易凭证**在后台查询并补开通，操作留有记录。

### 3.6 读者：被人问「你在这个站付过钱吗」

系统**不得**对外泄露任何会员身份。见 7.6。

## 4. 能力总览

系统需具备以下 9 项能力。第 5 章逐项展开。

| 编号 | 能力 | 一句话说明 |
|---|---|---|
| C1 | 采集 | 自动或人工触发，从一场比赛的多个直播间同时收集弹幕。 |
| C2 | 切片 | 把一场比赛的全部弹幕，按小局与节点切成可独立处理的片段。 |
| C3 | 规则统计 | 用确定性规则算出事实、时间轴、数量与密度。 |
| C4 | 情报报告 | 按固定结构生成一场比赛的情报报告。 |
| C5 | 发布 | 把报告发布成可公网访问的页面，并支持回滚。 |
| C6 | 会员与付费 | 收款、自动开通、到期降级。 |
| C7 | 站点统计 | 统计访问量与来源，区分免费页与付费页。 |
| C8 | 后台配置 | 管理员在页面上管理数据源与比赛。 |
| C9 | 通知与报警 | 异常时在时限内通知到运营者。 |

**贯穿全部能力的三条原则**

1. **事实优先**：任何输出的事实部分（比分、时间、数量）必须可回溯到原始记录；
   宁可慢，不可错。
2. **不丢证据**：原始弹幕记录只增不改，任何统计结果都必须能由原始记录重新算出。
3. **失败要响**：任何环节失败都必须发出可感知的报警，不得静默失败。

## 5. 功能需求

### 5.1 C1 采集

| 编号 | 需求 |
|---|---|
| FR-C1-1 | 系统能同时从**同场比赛的多个直播间**采集弹幕，且不重复、不遗漏。 |
| FR-C1-2 | 系统能对接**多个直播平台**；新增一个平台的采集能力，不得要求改动已有的平台采集逻辑。 |
| FR-C1-3 | 系统能发现一场比赛的可用直播间，优先级依次为：① 管理员手动指定 ② 由赛程信息关联 ③ 预先登记的候选池。三级之间需去重。 |
| FR-C1-4 | 采集能自动开始与自动停止（判定规则见 6.1），也支持管理员手动开始/停止。 |
| FR-C1-5 | 采集过程中出现断流、房间关闭、平台变更格式等情况时，系统需重试并报警，不得静默停止。 |
| FR-C1-6 | 每条弹幕记录至少包含：内容、发送时间、来源直播间、所属比赛。 |
| FR-C1-7 | 采集的运行状态（正在采集哪些比赛/房间、已收多少条、最后一次收到数据的时间）对管理员可见。 |

### 5.2 C2 切片

| 编号 | 需求 |
|---|---|
| FR-C2-1 | 系统能把一场比赛的全部弹幕，按**小局**切成若干片段。 |
| FR-C2-2 | 每个片段能进一步按**节点**（赛前 / 局中 / 复盘）归类。 |
| FR-C2-3 | 切片的边界必须由**确定的依据**决定（依据见 6.2、6.3），不得凭印象划分。 |
| FR-C2-4 | 系统需记录每个片段的边界来源（依据来自官方时间、弹幕信号还是人工确认），以便事后核对。 |
| FR-C2-5 | 切片结果需可被人复核、可被修正，修正后以修正结果为准且留痕。 |

### 5.3 C3 规则统计

| 编号 | 需求 |
|---|---|
| FR-C3-1 | 系统能算出每场比赛、每个小局、每个节点的**事实与统计**，至少包括：比分、击杀/关键事件时间轴、双方各项指标对比、弹幕总量与密度曲线、峰值与低谷时刻。 |
| FR-C3-2 | 系统能算出一场比赛各时间段的讨论热度变化，用于识别**讨论突然升温**的时刻（这是节点的候选信号之一）。 |
| FR-C3-3 | 系统能识别并统计**灰信号**（定义见 6.5），产出灰信号的类别、出现时间、密集程度与样本引用。 |
| FR-C3-4 | 规则统计的每一个数字都必须可回溯到原始记录（能回答「这个数是怎么算出来的」）。 |
| FR-C3-5 | 规则统计的结果必须可**由原始记录完整重建**：即使统计结果被删除，也能重新算出同样结果。 |
| FR-C3-6 | 系统能统计跨比赛的规律（如某支队在某类局势下的表现倾向），用于报告中的「规律」段落。 |

### 5.4 C4 情报报告

| 编号 | 需求 |
|---|---|
| FR-C4-1 | 系统能按**固定的分段结构**（见 6.6）生成一场比赛的情报报告。 |
| FR-C4-2 | 报告分**三个交付时点**：赛中快报（关键节点结束后尽快）、完整版（比赛结束后）、复盘版（赛后整理，面向免费读者）。 |
| FR-C4-3 | 报告的内容区分为两部分：**事实部分**与**解读部分**。事实部分必须与规则统计一致；解读部分必须明确标注为分析而非事实。 |
| FR-C4-4 | 报告必须声明其**取材范围**（采了哪些直播间、覆盖了哪些时间段），让读者知道结论建立在多少证据上。 |
| FR-C4-5 | 报告中的灰信号必须**只作为风险提示**呈现，不得出现指控性结论（见 6.5）。 |
| FR-C4-6 | 每份报告必须展示该场比赛的**节点进度**，让读者知道下一个节点与下一个交付时点。 |
| FR-C4-7 | 报告中出现的每个数字，读者都应能看到**来源说明**（数据与溯源）。 |
| FR-C4-8 | 报告在发布前必须经过**发布前检查**（见 6.7），不通过的不得发布。 |
| FR-C4-9 | 一份报告的修改必须以**新版本**形式发布，旧版本可追溯。 |

### 5.5 C5 发布

| 编号 | 需求 |
|---|---|
| FR-C5-1 | 报告需发布成**可公网访问的网页**，读者无需安装任何软件。 |
| FR-C5-2 | 页面必须能在手机上正常阅读。 |
| FR-C5-3 | 系统需提供**历史情报库**：按比赛、日期、联赛、队伍检索过往报告。 |
| FR-C5-4 | 系统需提供**画像库**：队伍与人员的长期表现摘要。 |
| FR-C5-5 | 系统需提供**灰信号统计页**。 |
| FR-C5-6 | 系统需提供**验证闭环页**：把过去的预测与后来发生的事实对照，公开对错。 |
| FR-C5-7 | 发布必须是**原子**的：一个页面上线时，与之相关的入口不得出现「页面已上线但入口显示暂无」的不一致。 |
| FR-C5-8 | 发布必须支持**秒级回滚**：发现错误时可立即恢复到上一版可用状态。 |
| FR-C5-9 | 发布失败不得导致站点不可访问；失败需报警。 |
| FR-C5-10 | 一场比赛结束后，该场所有节点页须**自动转为免费公开**。 |
| FR-C5-11 | 系统需在发布前检查**导航唯一性**与**旧模板残留**，不得出现重复导航或残留内容。 |

### 5.6 C6 会员与付费

**定价与档位**

| 编号 | 需求 |
|---|---|
| FR-C6-1 | 提供订阅档位：标准档与试用档；试用档的时间与价格显著低于标准档。 |
| FR-C6-2 | 定价与档位可由管理员调整，调整不影响已生效的会员。 |
| FR-C6-3 | 收款网络限定为 **Polygon 与 Solana** 两种，不接入其他网络。 |

**付款与开通**

| 编号 | 需求 |
|---|---|
| FR-C6-4 | 每位待付款用户获得一个**专属收款地址**与应付金额，该地址在本次付款中不与他人共用（Solana 侧若无法做到唯一地址，则必须用一个唯一标识区分不同用户的付款，具体方式由设计决定并要求可核验）。 |
| FR-C6-5 | 系统**自动检测入账**并自动开通，全程无需人工审核。 |
| FR-C6-6 | 开通必须是**幂等**的：同一笔交易无论被扫描多少次，都只开通一次、不重复累加。 |
| FR-C6-7 | 付款金额不足时，不静默失败，而是标记为「待补款」并明确告知用户还差多少。 |
| FR-C6-8 | 付款到账后，用户须在**无需等待人工**的情况下立即获得访问权。 |
| FR-C6-9 | 系统必须支持**事后补扫**：即使实时检测漏掉了一笔入账，也能在一段时间范围内重新发现它。 |
| FR-C6-10 | 系统必须提供**人工补开通**路径：管理员凭交易凭证即可核验并补开通，操作留痕。 |
| FR-C6-11 | 系统必须能在检测能力受限（如所用公共服务的调用额度被限制）时**报警**，而不是静默漏检。 |

**有效期与到期**

| 编号 | 需求 |
|---|---|
| FR-C6-12 | 会员自开通之日起有明确的有效期；有效期对用户可见。 |
| FR-C6-13 | 有效期将满时，系统提前提醒用户。 |
| FR-C6-14 | 到期后权限降级为访客，但保留**宽限期**（默认数天）避免误伤。 |
| FR-C6-15 | 系统需提供续费路径；续费从原到期日顺延。 |
| FR-C6-16 | 会员状态必须**可审计**：谁、何时、因哪笔交易、开通到何时，都必须有记录且不可篡改。 |

**资产安全（硬性）**

| 编号 | 需求 |
|---|---|
| FR-C6-17 | 系统**永不持有**用户的资产，也**永不持有**可动用收款资产的凭据。 |
| FR-C6-18 | 收款资产直达运营者自己掌控的地址；系统只负责**看见**入账，不负责**动用**。 |
| FR-C6-19 | 任何可动用资产的凭据一律不得出现在系统、文档、代码或配置中。 |
| FR-C6-20 | 系统不得要求用户连接任何浏览器插件或输入任何私钥来完成付款。 |

### 5.7 C7 站点统计

| 编号 | 需求 |
|---|---|
| FR-C7-1 | 系统需统计页面访问量，能区分**总访问**与**独立访客**。 |
| FR-C7-2 | 系统需能单独回答「**每天有多少人来过付费页面**」。 |
| FR-C7-3 | 系统需按页面排行，让运营者知道哪些内容更受欢迎。 |
| FR-C7-4 | 统计不得使用跨站跟踪手段，不得把访客数据交给第三方。 |
| FR-C7-5 | **系统无法**回答「来付费页的都是谁（具体身份）」，除非该访客主动留下联系方式或完成付款。这是隐私正确设计，不是缺陷（见 11 章）。 |
| FR-C7-6 | 必须建立「留资」与「付费」两类信息的关联能力，使得**自愿留资**或**付费**的访问者归属于可识别的个体。 |

### 5.8 C8 后台配置

| 编号 | 需求 |
|---|---|
| FR-C8-1 | 管理员能在页面上完成数据源与比赛的增删改查，**不需要**修改任何文件。 |
| FR-C8-2 | 配置改动在**一分钟内**对采集生效，无需重启系统。 |
| FR-C8-3 | 后台必须区分角色，非管理员不得访问任何后台页面。 |
| FR-C8-4 | 所有后台改动必须留痕（谁、何时、改了什么）。 |
| FR-C8-5 | 后台需展示采集健康状态与数据源可用性。 |

### 5.9 C9 通知与报警

| 编号 | 需求 |
|---|---|
| FR-C9-1 | 下列情况必须报警：采集中断、报告生成失败、发布失败、入账检测异常、磁盘将满、证书将过期。 |
| FR-C9-2 | 报警必须在 **5 分钟内送达**运营者；**超过 5 分钟未送达的报警须被丢弃**，不得延迟送达（避免无意义的迟到通知）。 |
| FR-C9-3 | 报警内容须包含：发生了什么、影响了谁、建议动作。 |
| FR-C9-4 | 报警不得重复轰炸：同一问题的重复报警需被合并或抑制。 |

## 6. 业务规则

本章的规则是系统行为的**判定依据**，必须完整实现且可被复核。

### 6.1 采集的开始与停止

**开始采集**，当且仅当满足：该场次已开播，且直播内容确为**在解说这场比赛**
（识别依据：直播标题/简介中出现对阵双方，或出现对应的联赛与赛事标识）。

**停止采集**，当满足任一条件：

- 直播中出现明确的终结表述（如「GG」「结束」「下班了」等），
- 或解说已开始讨论**下一场**比赛，
- 或既定的比赛结束时间已过且长时间无新弹幕。

### 6.2 阶段的判定（三层）

同一场比赛的弹幕，要同时按三层来理解，三层互不替代：

| 层 | 划分 | 用途 |
|---|---|---|
| **宏观阶段** | 赛前 → 选禁环节 → 局中 → 局间 → 赛后 | 决定当前属于「赛前情报」还是「赛后复盘」 |
| **节点** | 赛前节点 / 局中节点 / 复盘节点 | 决定**交付时点**：每个节点结束就应产出一份情报 |
| **小局** | 第 1 局、第 2 局…… | 决定切片的最小单位 |

### 6.3 切片窗口的来源（优先级）

小局与节点的边界，按以下优先级确定，**不得凭印象划分**：

1. **官方时间**：赛事方公布的开赛与结束时间。
2. **弹幕信号复核**：弹幕中出现的结束、比分等信息，经复核后用于修正边界。
3. **报告窗口**：已发布报告中所使用的时间窗口。

若三者冲突，以更高优先级为准，并**记录冲突事实**（供事后核对）。

### 6.4 终局判定

判定一场比赛「已终局」需满足：

- **至少 3 类相互独立的信号同时成立**，信号类别包括：
  1. 终结类弹幕出现**高密度聚集**并持续不短于 2 分钟；
  2. 比分与官方结果**核对一致**；
  3. 弹幕流量**降至峰值的一成以下**并持续不短于 5 分钟；
  4. 官方渠道或主播**明确宣布**比赛结束。
- **且此后 2 分钟内未出现反转**（如官方改判、比赛恢复）。

### 6.5 灰信号规则

**定义**：灰信号指弹幕中出现的、指向「比赛可能不正常」的讨论聚集现象。

**硬性约束**

1. 灰信号**只是风险提示**，报告与页面上**不得**出现任何指控性结论。
2. 不得指名指控任何个人或队伍。
3. 必须附**样本引用**（时间 + 原文片段），让读者自己判断。
4. 有**证据门槛**：单一来源或单一时刻的言论不构成灰信号；需**多人、多时段**的聚集。
5. 灰信号不得用于任何形式的勒索、威胁或交易。
6. 比赛结束后，灰信号页面的信息与报告保持一致。

### 6.6 报告的分段结构

每份报告**固定**按以下分段组织，顺序与标题不可随意增删：

| 段 | 标题 | 内容性质 |
|---|---|---|
| 0 | 比赛信息 | 事实 |
| 1 | 结果总览 | 事实 |
| 2 | 逐局复盘 | 事实 + 解读 |
| 3 | 队伍画像 | 解读 |
| 4 | 人员画像 | 解读 |
| 5 | 灰信号汇总 | 事实（风险提示） |
| 6 | 联赛规律与版本 | 解读 |
| 7 | 预测验证 | 事实 + 解读 |
| 8 | 盘口讨论 | 解读 |
| 9 | 情报含义与后续观察点 | 解读 |
| 10 | 数据与溯源 | 事实 |

### 6.7 付费墙的判定

- 付费墙的注入依据是「**该场比赛是否已结束**」，而不是依据页面文件名或目录规则。
- 判定「已结束」须综合下列事实，任一成立即可：结算信息已回填、全部小局均标记结束、比赛结果已回填。
- **禁止**按文件名或路径做一刀切判定（这会导致「已结束的比赛仍被锁」或「进行中的比赛被公开」）。

### 6.8 发布前检查

发布前必须逐项通过，**任一项不通过即不得发布**：

1. 全站导航唯一，无重复导航项。
2. 无旧模板残留内容。
3. 应受付费墙保护的页面，付费墙齐全；应公开的页面无付费墙。
4. 报告分段完整（对照 6.6 的十一段），无缺段。
5. 页面 × 联赛 × 标识的关联一致。
6. 无「速览卡」类残留物。

发布异常时：**保留上一版可用的站点**，恢复后再发布。

## 7. 非功能需求

### 7.1 时效

| 编号 | 要求 |
|---|---|
| NFR-T-1 | **赛中快报**：关键节点结束后 **2 分钟内**上线。 |

| NFR-T-3 | **复盘版**：比赛结束后 **15 分钟内**上线。 |
| NFR-T-4 | **数据源配置改动**：1 分钟内生效。 |
| NFR-T-5 | **报警**：5 分钟内送达，超时即丢弃（见 FR-C9-2）。 |

### 7.2 成本

| 编号 | 要求 |
|---|---|

### 7.3 质量

| 编号 | 要求 |
|---|---|
| NFR-Q-1 | 报告的**事实部分零错误**；数字、比分、时间须与官方一致。 |

| NFR-Q-3 | 解读部分须明确区别于事实部分，读者不得被误导为「事实」。 |
| NFR-Q-4 | 报告须可读：中文表达通顺，不使用未解释的行业黑话。 |

### 7.4 可用性与恢复

| 编号 | 要求 |
|---|---|
| NFR-A-1 | 站点须持续可访问；单次发布失败不得导致站点不可用。 |
| NFR-A-2 | 页面在手机上可正常阅读，首屏加载不为「慢到影响阅读」。 |
| NFR-A-3 | 系统须明确**可接受的中断时长**与**可接受的数据丢失范围**，并据此具备恢复能力（见 11 章待定项）。 |
| NFR-A-4 | 系统须具备**自动恢复**能力：进程异常退出后自动拉起。 |

### 7.5 安全

| 编号 | 要求 |
|---|---|
| NFR-S-1 | 系统任何位置（代码、配置、文档、日志）都不得出现可动用资产的凭据。 |

### 7.7 合规与边界

| 编号 | 要求 |

## 8. 验收标准

以下每条都必须能被**独立核验**。

| 编号 | 验收标准 |
|---|---|
| AC-1 | 给定一场已结束的比赛，系统能产出一份符合 6.6 分段结构、事实零错误的报告，并在承诺时效内上线。 |
| AC-2 | 给定一场**进行中**的比赛，会员能看到当前节点的情报，访客看不到；比赛结束后，该场自动转为所有人可见。 |
| AC-3 | 一位读者从打开订阅页到获得访问权，**全程无需人工干预**，且款项直达运营者控制的地址。 |
| AC-4 | 同一笔付款被重复检测多次，只开通一次。 |
| AC-5 | 故意让实时入账检测漏掉一笔（模拟调用额度受限），事后补扫能发现它；管理员也能凭交易凭证补开通。 |
| AC-6 | 会员到期后降级为访客，宽限期内仍可访问；续费从原到期日顺延。 |
| AC-7 | 管理后台的非管理员入口不可访问；配置改动 1 分钟内生效。 |
| AC-8 | 发布前检查任一项不通过时，系统拒绝发布且站点保持可用；发布失败后可立即回滚。 |
| AC-9 | 站点统计能单独回答「某天有多少人来过付费页」，且**无法**回答具体是谁（除非其主动留资或付费）。 |
| AC-10 | 会员校验接口在查询「不存在的账号」与「未开通的账号」时，响应**不可区分**。 |
| AC-11 | 采集中断、发布失败、入账检测异常、磁盘将满、证书将过期，均产生 5 分钟内送达的报警。 |
| AC-12 | 项目全库检索，**零命中**任何可动用资产的凭据。 |
| AC-13 | 删除全部统计结果后，系统能仅凭原始记录与配置重新算出同样的统计（可重复验证）。 |
| AC-14 | 自动化测试覆盖率 ≥ 90%，且在无外网条件下可重复运行。 |
| AC-15 | 在一场比赛中同时采集多个直播间、跨多个平台，结果不重复、不遗漏，且能说明每场直播间的贡献量。 |
