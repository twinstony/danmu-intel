# ADR-0018 站点统计自建：每日盐、访客哈希、90 天保留与「答不了是谁」

## 状态：已接受

## 上下文

需求 FR-C7-1..6 / §6.7 / AC-9 / NFR-P-3/4、设计 §11.4 与 §13、ADR-0001（Funnel 暴露
「校验 / 统计上报 / 下单」）、ADR-0009（付费可见性只由比赛状态机驱动）、
ADR-0015 决策 1（站点树清单与路径）、ADR-0017（凭据 cookie 的形态与 SameSite）。

设计与需求把「要什么」定得很清楚（自建、不跨站跟踪、区分总访问与独立访客、
答得了「某天多少人来过付费页」、答不了「是谁」、明细 90 天→汇总），但**没写到实现级**：

- 每日盐从哪来、什么时候换、要不要留旧盐；
- 访客哈希到底怎么拼（顺序、分隔符）—— 这决定了两天后还能不能把同一个人认出来；
- 「付费页访问」在**采集那一刻**定，还是把汇总留到月底再算（比赛中途结束会翻转可见性）；
- 明细到期「汇总入 `stats_daily`」由谁触发、谁来保证不丢账；
- 「下单转化 / 留资数」这两个数字从哪来（站点统计只看得见页面访问，看不见订单）；
- 前端 beacon 写在页面哪里，会不会破坏 T5/T7 立下的「静态页零脚本、无第三方请求」纪律；
- `member_id` 到底由谁给：客户端自称的身份能不能采信。

## 决策

1. **每日盐 = 当天随机盐，只留一行**（`stats_salt`）。第一次上报碰到新的一天就
   `secrets.token_hex(32)` 生成、**删掉旧盐**，因此不需要 cron、也不需要新凭据：
   有请求的那一刻盐已经是当天的，而昨天的哈希再也算不回来（AC-9 后半段）。
   不落旧盐是有意的：留着旧盐就能跨日暴力还原「同一个人」。
2. **独立访客口径照需求原文**：`sha256(每日盐 + IP + UA)`。盐是 64 位定长十六进制，
   拼接因此无歧义（不加分隔符，也不改口径）。IP 与 UA **只在内存里活一次**，
   进库的只有 `visitor_hash` —— `stats_events` 里没有 IP / UA / 联系方式字段。
3. **付费页分类在访问那一刻冻结**（`stats_events.paid`）。判据只有比赛状态机
   （`paywall.visibility(matches.state)`，ADR-0009）：路径只用来找到「哪场比赛」
   （`matches/<id>/index.html` 与 `matches/<id>/<形态>.html`），文件名/路径永远不是判据。
   比赛当天结束后再回填汇总，也不会把「昨天的付费页访问」改写成公开页访问。
4. **汇总是明细的耐久副本**：`stats_daily` 只存明细能算出来的五个计数
   （`page_views` / `sessions` / `unique_visitors` / `paid_page_views` / `paid_unique_visitors`）。
   设计 §13 的 `leads` 列**没有落进汇总表**：留资留在 `members` 账本里（NFR-P-4「留资不与
   统计明细混存」），汇总表多存一份只会产生「谁更新」的第二个真相源。
5. **裁剪先汇总再删**（`daily.prune`）：保留期（90 天）之外的日期先 `rollup` 写
   `stats_daily`、再删明细，因此裁剪不丢账、汇总后仍答得出那天的口径；明细已被裁剪的日子
   永远不会被「空明细」改写成 0。会话口径 = 同一访客两次访问间隔 ≥30 分钟算新会话
   （没有客户端会话 ID，这是自建统计能做到的确定性近似，且由明细唯一确定）。
6. **下单转化与留资从各自账本算，不进统计表**：`orders.created_at` /
   `orders.paid_at` / `members.created_at` 是长期保留的账本，任何一天都能事后重算，
   因此不复制进 `stats_daily`（复制会产生「入账晚到导致昨天数字变旧」的问题）。
   转化率 = 下单数 ÷ 当日**付费页人数**（分母为 0 时如实说「—」，不编数字）。
7. **对外只出计数**：`GET /api/stats/daily?day=` 的响应字段是固定的九个计数
   （`day` + 五项访问 + `leads` / `orders` / `paid_orders`），没有任何 IP / 访客哈希 /
   身份字段 —— AC-9「答不了一个人是谁」在这层是**逐字段可断言**的。要回答「是谁」只能走
   `members` / `orders` 账本，也就是 AC-9 的「除非其主动留资或付费」。
8. **`member_id` 只认凭据、不认自称**：beacon 的请求体里没有身份字段，服务端只在
   `Cookie` 里的凭据**校验通过**时把它记进 `member_id`（FR-C7-6 的「自愿留资/付费者
   归属于可识别个体」）。跨站部署（Vercel 页面 → Funnel API）时 `SameSite=Lax` 的凭据
   cookie 本来就不会被带上 —— 那就如实记空，宁可少一条关联，也不接受客户端自称的身份。
9. **前端 beacon 写在站点树这一层，配了 API 基址才写**：一次发布写出的每一页（含
   `report/html.py` 渲染的报告页）都在 `</body>` 前注入一行内联脚本，
   `navigator.sendBeacon(<api_base>/api/stats/beacon, {page})`（`text/plain`，跨源免预检，
   响应被丢弃）。**没配 `billing.api_base` 就不写脚本**，静态站仍是零脚本；
   脚本里没有任何第三方地址 —— T5/T7 的「无第三方请求」纪律保持成立，只是从
   「零脚本」精确成「零第三方、唯一脚本是自建上报」。渲染器改了结构（没有 `</body>`）
   就让发布报错，而不是静默丢掉统计。
10. **上报要限流**（NFR-S-2）：按 IP 分桶（120 次/分钟），越限返回与其它写接口同一形态的
    429；上报成功返回 **204 无内容** —— 没有响应体就谈不上泄露。

## 后果

- ✅ AC-9 的两半都可测：`paid_unique_visitors` 答得出「某天多少人来过付费页」；
  次日换盐后的哈希与昨日不可关联，且日汇总响应逐字段断言无身份/网络字段。
- ✅ FR-C7-1/2/3/4 有落点：总访问与独立访客分列、付费页单独计数、按 `page` 可排行、
  不加载第三方脚本也不向第三方发送任何数据。
- ✅ FR-C7-6 的「关联」是**能力**而不是**暴露**：`member_id` 只在凭据通过时落库，
  对外的统计回答仍然只有计数。
- ⚠ 跨站部署（Vercel 站点 + Funnel API）下 `SameSite=Lax` 的凭据 cookie 不会随 beacon 送出，
  因此漏斗里的「已识别访客」在那种拓扑下恒为空 —— 这是刻意的取舍（第 8 条），
  若将来把站点与 API 收到同域，这条关联会自动开始工作，无需改代码。
- ⚠ 会话近似（30 分钟缺口）不是浏览器会话：同一个人换 IP/UA 就是两个访客（口径如此），
  同一台设备换网络也会被算成两个人 —— 这是「不采集跨站信息」的代价，需求选择了它。
- ⚠ 90 天保留由运维的 cron 触发（`danmu-intel site-stats --prune`），不引入调度器依赖
  （与 T9 的 `members --sweep` 同一路子）；哪怕不跑，明细也只是多留几天，数字不会错。
