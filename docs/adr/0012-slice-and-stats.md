# ADR-0012 切片优先级的裁决语义与统计的可重建性

## 状态：已接受

## 上下文

需求 §6.3 给了三级边界依据（官方 > 弹幕信号 > 报告窗口）并要求「冲突时以高优先级为准
并记录冲突事实」，FR-C2-5 又要求「切片可被修正，修正后以修正结果为准且留痕」。
设计 §8.1 把 `manual` 排在优先级表的第 4 行，§9.2 定了终局判定，§9.3 定了
「`algo_version` 随算法变更递增；重算写新行，不覆盖旧行」，§9.1 把灰信号门槛放进
`config` 表。Ticket #7（T4）落地时必须回答几个文档没写到语义级的问题：

- `manual` 到底是「第 4 个证据来源」还是「覆盖机制」？如果是证据来源，人工把边界改对了
  反而会被官方数据重新盖回去（FR-C2-5 就作废了）。
- `algo_version` 由谁递增？AC-13 要求删掉统计后能重算出同样结果，那么版本号就不能由
  时钟或进程状态决定，必须**由输入唯一确定**。
- 「重算写新行、不覆盖旧行」与 AC-13「删全部统计重算结果一致」怎么共存？
- 弹幕信号「≥2 类独立信号」里的「独立」是谁来保证？
- 灰信号的门槛与关键词放哪，才能既满足 §9.1 第 4 条（写 config、改动留审计）又不让
  纯函数层去读库？

## 决策

1. **优先级只管证据，修正永远覆盖。** `official > danmu_signal > report_window` 是
   **证据来源**之间的裁决顺序；`manual` 是**修正机制**，不是第四个证据来源。存在带留痕
   的人工修正时它胜出（FR-C2-5），且 `apply_boundaries` **绝不用自动来源覆盖有人工修正
   的切片**（跳过 + 写一条 `slice.boundary` 审计说明为什么没写）。无论谁胜出，只要多来源
   给出的**边界不同**，差异一律写进 `slices.conflict_note`（**冲突必记录**，即使高优先级
   胜出、即使被人工覆盖）。
2. **「≥2 类独立信号」用信号类别保证独立性**：`lexical`（说了什么）/ `density_shift`
   （说了多少）/ `score_mention`（提到了比分）三类互不依赖。候选边界以**词法锚点**为中心
   聚拢 `±120s` 内的其它信号，类别数 <2 即复核不通过并把原因写进复核结果（`note`），
   未通过复核的候选**永远不参与裁决**。
3. **`algo_version` 由审计记录推导**：基础版本（`stats.basic.ALGO_VERSION`）+
   `+ov{N}`，`N` = 该场 `slice.override` 审计条数。每次人工修正写一条审计、版本递增一级；
   重复执行同一修正（边界没变）不留痕也不递增。版本号因此只由输入决定 ——
   删掉统计后重算，版本号仍可复现（AC-13）。
4. **`metrics` 按算法版本分片**：重算只清并重写**当前版本**的行，旧版本永久保留
   （§9.3「旧版本不删」）；AC-13 比对的是当前版本的行（历史版本对应的算法已不存在，
   本来也无法重建）。
5. **配置只在读库处注入**：门槛与关键词表进 `config` 表的 `stats` 键（JSON），
   纯函数层只接受 `StatsConfig` 入参（§9 铁律「不读全局状态」）。改配置写一条
   `config.update` 审计。
6. **统计全集含中立指标**：除密度/峰值/低谷/比分/击杀轴外，加 `neutral` 指标
   （双方提及量 + 中立弹幕量），只计数、不褒贬、不归因 —— FR-C3-1 的「双方各项指标对比」
   在没有结构化双方数据前只能用这个口径，且必须标明是计数而非评价。
7. **终局判定三态 `final | live | revoked`**，观测窗口未覆盖 2 分钟反转窗口时保持
   `live`（**宁可不判，不可误判**）。「曾判定、已撤销」的事实保留在判定结果里
   （`satisfied_at_ms` + `reversal`）。
8. **灰信号硬约束落在结构与渲染两层**：产出物 `GraySignal` 结构上装不下身份字段；
   `report/rule_render.py` 出口前逐一比对全部 `user_hash`，出现即抛错；样本非空是
   **落库前置校验**；不提供任何导出接口；不达标即 `discarded` 且必填原因，`discarded`
   不进报告。

## 后果

- ✅ FR-C2-3/4/5、FR-C3-1/3/4/5、需求 §6.4/§6.5、AC-13 都可测：切片来源与冲突、修正留痕
  与版本递增、终局判定三条硬用例、灰信号「单人单时段不产出」、渲染零身份，都有测试。
- ✅ 统计层保持纯函数：AC-13 的重算断言逐字节相等（含浮点规整与排序）。
- ✅ 灰信号的六条硬约束里，第 1/2/3/5/6 条有机器可查的落点（状态机常量、渲染防线、
  落库校验、源码扫描测试），第 4 条由 `config` 门槛 + 审计落地。
- ⚠ 官方数据源仍是开放项（设计 §20 O8）：`official_result` 的 JSON 形状由
  `common/official.py` 先定下来，人工登记与将来的抓取器共用同一契约。
- ⚠ 灰信号关键词表只是初值（设计 §20 O7 建议从蓝图实证迁移，本仓库拿不到蓝图），
  已做成 config 可覆盖，等有实证再换。
- ⚠ `escalated` 状态由 T12 后台人工翻，本层只保证重算不覆盖它。
- ⚠ 「比分/击杀轴」在缺官方数据时用弹幕抽取，只作**来源标记**，报告里必须写明来源
  （事实层零错误的前提是「缺就说缺」，见 NFR-Q-1）。
