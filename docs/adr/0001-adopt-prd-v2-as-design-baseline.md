# ADR-0001：采用 PRD v2.0 作为设计基准，不从零设计

- **状态**：已采纳
- **日期**：2026-09-21
- **决策者**：用户

## 背景

立项「danmu-intel」时，目标是做出 `danmu-intel-local` 的「更好版本」。存在两种做法：

- **A**：从零重新设计产品与工程。
- **B**：以蓝本中已存在的云端工程版 PRD 为基准实现。

调研发现蓝本 `docs/task/DANMU_INTEL_CLOUD_PYTHON_PROJECT_PRD.md` 已是 **v2.0 完整设计定稿（2026-08-31，状态：待开发）**：17 节、756 行、12 个功能层，涵盖架构原则、四步加工引擎、节点与 SLA、成本预算、免费/付费边界、十段结构、测试与验收标准。

同时 PRD §0 第 4 条已明确规定本项目最关心的自动化诉求：

> 架构遵循「程序固化 + LLM 只走接口」：流程/材料/方法全部程序化，LLM 仅通过固定提示词 + 数据调用，**不依赖 Codex 会话**。

## 决策

**采用方案 B**：直接以 PRD v2.0 为设计基准实现，不从零设计。

本项目的新增工作聚焦于 **PRD 未覆盖的两个缺口**：

1. **付费闭环**：PRD §7.9 订阅层仅 4 行（「登记表单 → 推送站长 TG」），且与 §16 验收第 8 条「订阅链路全自动」自相矛盾。
2. **生成路径收敛**：蓝本并存三条生成路径互相打架，PRD §2.2 点名此为「四类失效模式」之四（格式混乱）。

## 后果

- **正向**：省去重复设计；产品逻辑、SLA、成本、验收标准均已有定稿可依；执行体有唯一权威文档。
- **负向**：需在 PRD 之上明确「哪里是改动、哪里是沿用」，避免执行体误读为从零重写 → 由 `docs/design/DANMU_INTEL_DESIGN.md` §2.2 差异表承担。
- **约束**：PRD 中与实际不符处（如早鸟截止已过期）必须显式提出并修正，不得静默沿用。
