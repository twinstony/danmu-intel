# ADR-0017 会员付费全自助闭环：xpub 派生、Solana memo、订单状态机、防枚举与凭据

## 状态：已接受

## 上下文

需求 FR-C6-4..21 / AC-3/4/5/6/10/12/18、设计 §12.1–12.6、§14.4、§18（S3 支付决策缝、S4 HTTP 边界缝）、
ADR-0001（Funnel 暴露「下单 / 校验」接口）、ADR-0004（Polygon 派生 + Solana memo）、
ADR-0005/0016（链上监听：Transfer / 游标 / 补扫 / 额度告警）、ADR-0006（全自助 + 防枚举 + 凭据只存哈希）、
ADR-0009（付费可见性只由状态机驱动）、ADR-0015 决策 3（付费正文只经 API 返回，「HTTP 层属 T9」）。

设计与 ADR-0006 把「怎么做到」写到了流程级，但**没写到实现级、必须在实现时定死**的有：

- xpub 从哪来、路径与索引如何不重复、错层级或错前缀（xprv/ypub）怎么处理；
- 在「零新依赖、断网可跑、永不持有可动用资产凭据」的约束下，keccak 与 secp256k1 从哪来；
- 订单的金额形状（同额多单怎么区分）、复用规则、过期语义、给用户看的短引用；
- **凭据到底发给谁、凭什么发**：设计说「用户凭通讯账号领取凭据」，但只凭账号就等于
  「谁知道你是会员，谁就能领走你的访问权」；
- 校验接口如何做到「不存在 / 未开通 / 已过期」逐字节相同，同时会员又能真的拿到凭据；
- 一笔入账怎么对上订单；重复、多付、不足额、对不上账分别怎么办；
- 宽限期与续费的时间语义（从原到期日顺延，对已经过期的人怎么办）；
- 没有调度器的情况下，到期降级由谁触发；
- 付费正文接口（D4 的落点）与凭据怎么绑定；
- `members` / `orders` 之外还缺哪些表（逐笔入账、凭据哈希、限流桶）。

## 决策

1. **收款地址**：Polygon 从**账户级 xpub**（BIP44 的 `m/44'/60'/0'`，depth=3）按
   `m/44'/60'/0'/0/i` 做**非硬化**派生，索引**只前进**（`orders.address_index` 取 `MAX+1`，
   已展示给某个人的地址永不分配给他人 —— 设计 §12.2 ⑧ 防串单）。Solana 用**单一收款地址 +
   每单唯一 memo**（`memo = public_ref`，ADR-0004 允许的"唯一标识"）。
   派生前一律做四项校验：**拒绝 xprv/yprv/zprv**（扩展私钥）、**拒绝硬化派生**（要私钥，系统没有）、
   **拒绝非 depth=3**（层级不对会算出别人的地址，钱就收不到了）、拒绝非 `xpub` 前缀的文本。
   xpub 与 Solana 收款地址存 `config` 表的 `billing` 键：它们是**公开信息**（watch-only / 收款地址），
   不是可动用资产的凭据，因此可以进库、可以后台改，改动照样写 `audit_log`。

2. **零新依赖的密码学**：自己实现 keccak-256、secp256k1 点加与标量乘、base58check、BIP32 CKDpub
   （`billing/crypto.py` + `billing/xpub.py`，共约 230 行）。理由是约束决定的：成熟库要么带编译依赖
   （`coincurve`）要么附带**签名能力**（`eth-keys`、`bip-utils`），而后者的攻击面我们不需要 ——
   本系统只需要「公开信息 → 地址」这一条**单向**path，运行约束是单机、断网、零新依赖（NFR-A-3 / AC-14）。
   正确性不靠自证：BIP-0032 官方向量 1（主 xpub、链码、公钥）、keccak-256 已知常量、secp256k1 已知标量点、
   一条**参考实现独立算出**的 xpub → `0/i` 地址链、EIP-55 官方四条测试向量，全部写死在测试里
   （`tests/unit/test_billing_xpub.py`）。同时给 `tools/check_no_secrets.py` 加一条「扩展私钥」模式：
   `xprv…` 一出现就拦（AC-12 的防线跟着这一票变强）。

3. **订单形状**：`amount_due_units` = 档位价 + **唯一尾数**（1..999 最小单位，在该网络的未付订单内唯一），
   同额多单因此可区分（设计 §12.2 ④）；`public_ref` = `DM` + 8 位十六进制（唯一，Solana 当 memo）；
   有效期 30 分钟（`billing.order_ttl_ms` 可配）。金额一律**最小单位整数**（USDT 6 位小数），钱不用浮点算。
   同一个（通讯账号，档位，网络）已有未付订单 → **复用**该订单、不生成新地址（设计 §12.2 ②），
   只轮换领取令牌。

4. **领取令牌（claim token）**：下单时下发一枚 32 字节随机令牌，**库里只存哈希**，明文只在下单响应里
   出现一次，**不写进链上 memo**（链上 memo 用的是公开的 `public_ref`）。它是「下单的那个浏览器」
   与「已付款订单」之间的绑定物。

5. **领取与校验分成两个动作**（这一步是设计没写、但必须定死的）：

   | 动作 | 入参 | 成功条件 | 产出 |
   |---|---|---|---|
   | `claim` 领取 | 通讯账号 + 订单引用 + **领取令牌** | 三者与同一张**已付款**订单一致，且该会员仍可访问 | 一枚凭据（32 字节，只存哈希）→ `Set-Cookie` |
   | `verify` 校验 | **凭据**（cookie 或 body 里的 `code`） | 凭据有效且会员还能访问（`active`/`grace`） | 会员状态与有效期（对外可见，FR-C6-12） |

   `verify` 的 `platform`/`username` 字段**只用于按账号限流分桶，不参与判定** ——
   一旦它参与判定，这个接口就变成了会员名录（NFR-P-2 要禁的正是这件事）。
   Cookie 属性：`HttpOnly; Secure; SameSite=Lax; Path=/`，`Max-Age` = 剩余有效期（到期即失效）。

6. **防枚举的最强形态**：失败路径**逐字节相同** —— 账号不存在、存在但未开通、已过期、已撤销、
   凭据不对、账号标识非法、**被限流**，全部是同一份 `NEUTRAL_BODY` 与同一个状态码（200）。
   成功路径必须能与失败区分（否则会员拿不到自己的凭据），区分方式**只有凭据本身**。
   这条同时满足 AC-10（三种情况不可区分）与 NFR-P-2，并且比"只区分成功"更强：连接口
   回答「某账号是不是会员」都做不到。「谁知道你是会员，谁就能领走你的访问权」这一条由
   **领取令牌**堵住：光知道账号领不走（令牌只在下单的那个浏览器里）。
   ADR-0006 说的「凭据重发走通讯渠道核验」留给 T11（现在没有对外通讯渠道可用）。

7. **限流按 IP 与按账号两维度**（NFR-S-2），桶是 `rate_limits` 表的固定窗口计数：
   `claim` 按账号 5/小时 + 按 IP 20/小时；`verify` 按 IP 60/分钟；`POST /api/orders` 按 IP 30/小时；
   付费正文按 IP 60/分钟。`claim`/`verify` 被限流返回**中性响应**（不给攻击者额外信息），
   下单被限流返回 429（那里没有身份信息可泄露）。

8. **对账是一个纯函数**（设计 §18 的 S3 缝）：`settle(conn, transfers)`。
   候选订单：Polygon 按小写地址、Solana 按 memo；资产必须是我们收的 USDT
   （Polygon 的合约地址大小写不保证 → 比小写；Solana 的 mint 逐字节比）。
   逐笔入账写 `order_payments`（`tx_ref` 唯一 = 幂等键）；累计金额
   **足额** → 订单转 `paid` + 开通；**不足** → 订单转 `short` + 记差额 + 写「待补款」通知（FR-C6-7）；
   **对不上账**（找不到订单 / 资产不是 USDT）→ 通知（设计不静默漏一笔钱）；
   **已付订单又多收一笔** → 通知且**不再开通一次**；**开通失败** → `critical` 通知（设计 §15 第 7 行）。
   到期未付的订单由同一函数先标 `expired`。

9. **开通幂等有两层**：`order_payments.tx_ref` 唯一（同一笔入账只记一次）+
   `members.grant(tx_ref)` 以审计里那条 `billing.member.granted` 为幂等键（同一笔交易只顺延一次）。
   第二层让「人工补开通 + 事后补扫认出同一笔」也不会重复累加有效期（AC-4 的完整形态）。

10. **时间语义**：会员 `active`/`grace` 且 `expires_at + grace_ms > now` → 续费**从原到期日顺延**
    （AC-6 原文）；已经过了宽限期或首次开通 → 从此刻起算（把死掉的日期往后加没有意义）。
    宽限期内**仍可访问**：`Member.can_access(now, grace_ms)` 是纯函数，读路径不写状态。
    降级由 `danmu-intel members --sweep` 触发（cron 友好），每次转换写
    `billing.member.grace` / `billing.member.expired` 审计。

11. **监听目标从订单派生**：`chain-watch --orders` 用 `settle.watch_targets()` 生成目标
    （未过期未付清的 Polygon 派生地址 + Solana 单地址），**不看也不用人工填地址**（AC-3）。
    过期订单的地址不再轮询：额度是有限的（ADR-0016 决策 5 的两条路径），过期后到账的钱由
    「人工补开通」或显式地址补扫处理 —— 这一点在后果里写明。

12. **付费正文接口是这一票的落点**（ADR-0015 决策 3 把 HTTP 层留到这里）：
    `GET /api/report/<id>/<kind>/paid` —— 凭据有效**或**比赛已结束才返回正文，
    判定直接复用 `publish/access.py`（不写第二遍），否则 403（不泄露比赛是否存在之外的东西）。

13. **表结构增补**（`common/db.py`，不迁移）：`members`（设计原样）、
    `orders`（设计原样 + `tier` / `claim_hash` / `address_index` —— 档位是定价与试用判定的依据，
    令牌哈希是领取的权限，索引是只前进的派生游标）、`order_payments`（逐笔入账与幂等键）、
    `member_credentials`（凭据哈希 + 最后使用时间 + 撤销时间）、`rate_limits`（限流桶）。

14. **凭据绝不明文落库**：只存 `sha256`；审计只记「谁何时领了一枚凭据」，**不记凭据本身**；
    异常与日志里没有令牌/凭据的值。仓库外 `.env`（0600）继续只放**查询类** API key
    （`POLYGONSCAN_API_KEY` / `HELIUS_API_KEY`），xprv 与私钥一律不得出现（AC-12）。

15. **价格默认值**（设计 §20 O1 的开放项，先给出可跑的起点）：标准档 **5 USDT / 30 天**、
    试用档 **0.5 USDT / 3 天**，全部存 `config` 的 `billing` 键，`danmu-intel billing --set` 可改、
    改动留审计。定价直接以链上收款资产（USDT）计，**不做汇率换算**（避免引入行情源这一层）。
    收款资产固定为两链的 USDT（公开常量）：Polygon ERC20 合约、Solana SPL mint。
    试用档每位会员只享受一次（从「已付的 trial 订单」派生判定，不加冗余字段）。

## 后果

- ✅ **AC-3 全程无人工**：`POST /api/orders` → 链上入账（`chain-watch --orders`）→ 自动开通 →
  `POST /api/claim` 领凭据 → 读付费正文，e2e 在断网下逐条断言（`tests/e2e/test_billing_loop.py`）。
- ✅ **AC-4 只开通一次**：两层幂等键（逐笔入账唯一 + 开通按 `tx_ref`），重复检测、多付、人工补开通
  三种情形都不再累加有效期。
- ✅ **AC-5 漏检可找回**：限速那一轮看不见入账但不静默（T8 的报警），恢复后补扫认领同一笔；
  人工路径用 `grant --tx-ref --reason` 补开通，审计留痕且同样幂等。
- ✅ **AC-10 不可区分**：六种失败（含被限流）响应逐字节相同，在真 HTTP 上被断言
  （设计 §18 的 S4 缝；判定其实在纯函数里，所以这条也能在单测里断言）。
- ✅ **AC-12 零凭据**：系统里只有 xpub、派生地址、memo、收款地址与 API 查询 key；
  没有私钥、没有助记词、没有 keystore，也**没有任何签名能力**；扫描器新增「扩展私钥」模式，
  pre-commit 与测试双重阻止其入库。
- ✅ **定价可改**：改价格不影响已生效的会员（`expires_at` 是开通那一刻算好的死日子）。
- ⚠ **偏离说明（AC-18 / FR-C6-21 的解读）**：需求说「会员仅凭既有通讯账号标识即可完成校验」。
  本实现里，通讯账号是**领取**（claim）的入参之一，校验（verify）靠凭据。
  逐字实现「只凭账号就能校验」等于「凭账号就能领走别人的访问权」（没有对外通讯渠道可用于
  二次核验），因此把「凭证的交付」绑到 `claim`（账号 + 订单引用 + 领取令牌）上。
  这一条的收紧（凭通讯渠道核验后重发）属 T11。
- ⚠ **只收两链的 USDT**：原生 MATIC/SOL 到账会记「对不上账」并写通知（人要能看到这笔钱，
  而不是被静默当成无效入账）。要收别的资产时改 `pricing.USDT` 与档位定价，不改形状。
- ⚠ **过期订单的地址不再轮询**：付晚了的钱不在日常扫描范围内（额度约束），
  走「人工补开通」或显式地址补扫；这一点是刻意的取舍，不是遗漏。
- ⚠ **到期降级需要外部触发**：`members --sweep` 交给 cron（本项目不引入调度器依赖）。
  哪怕没人跑它，`can_access` 与 `verify` 也会按时间正确判定 —— sweep 只是把状态写实、留痕。
- ⚠ **凭据靠 cookie**：换设备/清 cookie 后要重新 claim（需要订单引用 + 领取令牌）。
  两种都丢了就走人工或 T11 的通讯渠道核验。
- ⚠ **xpub 泄露的后果**（承接 ADR-0004）：所有派生地址暴露，但资金仍然安全
  （私钥在运营者硬件钱包里，系统只有 watch-only 信息）。
- ⚠ **`serve` 是前台进程**：公网暴露靠 Tailscale Funnel 转发，托管与 Funnel 配置属运维
  （ADR-0001），不在本层代码里。
