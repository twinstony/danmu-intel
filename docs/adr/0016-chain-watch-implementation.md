# ADR-0016 链上监听的实现：按地址游标、双重路径、额度记账与告警闸门

## 状态：已接受

## 上下文

ADR-0005 定了「Polygon 走 Polygonscan、Solana 走 Helius、用量 >80% 或限速就报警、补扫按地址查
历史」，设计 §12.2 第 ⑤ 步与 §12.7 定了「每 60 秒轮询 + 启动时补扫」、`chain_cursors` 与
`quota_usage` 两张表的形状。需求侧约束是 FR-C6-11（能力受限必须报警，不静默漏检）、AC-5
（故意漏掉一笔，事后补扫能发现它）、NFR-C-3（随时可查当日/当月成本）、AC-12 / FR-C6-17..19
（系统永不持有可动用资产的凭据）。

设计写到「表结构 + 每 60 秒轮询」为止，**没有**写到的、必须在实现时定死的：

- 游标的**粒度**：一条链一个全局游标，还是**一个地址一个**游标；
- 两条链的游标语义不同（区块号有大小序、签名没有），要不要假装统一；
- 「增量」与「补扫」到底差在哪一步（差在要不要读游标之外还有别的吗）；
- 一笔链上入账在本系统里是**什么形状**（两条链字段差异往哪放）；
- 额度记账的**窗口**与**单位**（Polygonscan 按天计次、Helius 按月计 credit，形状不同）；
- 「限速」的处理方式：退避重试，还是**报警**；
- 告警的**去重单位**（每 60 秒重判一次阈值，不去重就是每 60 秒一条重复通知）；
- 供应商**端点**的现状（`api.polygonscan.com` 已 301 迁移）；
- 「后台可查当日/当月成本与额度」在后台（T12）落地之前由谁提供。

## 决策

1. **入账只有一个形状 `Transfer`**（`chain/transfer.py`）：`network`、`address`、`tx_ref`、
   `asset`（`native` 或代币标识）、`units`、`at_ms`、`memo`、`block`。金额一律是**最小单位
   整数**（wei / lamports / 代币最小单位），与 `orders.amount_due_units` 同一口径 —— 钱不用
   浮点算。`tx_ref` 是幂等键（Polygon 是 tx 哈希，Solana 是签名），订单匹配（T9）只需要这
   一个类型，不需要知道任何链上细节；`network` 只允许 `polygon` / `solana`（设计 §12.5 白名单，
   明确排除 Base）。

2. **游标管到地址一级**：`chain_cursors(network, scope)` 的 `scope` 就是被监听的收款地址。
   按链存一个全局游标是错的 —— 多地址共用时，一个地址的入账会被另一个地址推进的游标越过去，
   只能靠补扫兜底；管到地址一级，「断点续扫」才是精确的，补扫退回第二道保险。

3. **两条链的游标语义如实表达，不假装统一**：`polygon` 的游标是「已处理到的最新入账区块」，
   `advance` 对它做**单调保护**（只前进不回退 —— 回拨等于把扫过的区间再扫一遍，最坏把同一笔
   付款当成两笔）；`solana` 的游标是「已处理的最新签名」，签名没有可用的大小序，夹不住，因此
   只由调用方「真的处理完新签名才写」保证单调。两链都只在**真的推进了记录**时才写游标：没扫到
   东西就是没扫到，不假装进度。

4. **增量 = 从游标的下一块起扫；补扫 = 完全不读游标**（`watcher.py` 的 `poll` / `rescan`）。
   Polygon 的 `from_block = 游标 + 1`（同一区块的多笔入账上一次已经一起拿到，不重复扫也就不会
   重复报）；Solana 传 `until=游标签名`（节点语义：只回它之后的新记录）。`rescan` 走
   「按地址查全历史」的同一批接口但不传游标 —— 于是它**天然**能发现游标坏掉/跳掉时漏掉的付款
   （AC-5）。两条路径是互为兜底的两条独立路径，不是冗余。

5. **启动补扫 + 每 60 秒增量轮询**（`POLL_SECONDS = 60.0`，设计 §12.2 ⑤）：`Watcher.run()`
   先 `rescan()` 再进循环；`on_transfer` 回调是产出的唯一出口（看见一笔立刻交出去，不让调用方
   等循环结束 —— 订单匹配属 T9）。CLI 是 `danmu-intel chain-watch`（可 `--once` / `--rescan` /
   `--interval` / `--seconds`，后者让长驻与「跑一轮」两种用法都有）。**某个地址扫描失败不影响
   其它地址**：失败原因如实放进 `Observation.failures`，CLI 据此返回非 0。

6. **额度记账按供应商按日累加**（`quota_usage(provider, day)`，只增不改）：`calls` 与 `credits`
   都记，`last_error` 记**最近一次**调用的结局（成功即清空 —— 它回答「现在还出不出问题」，
   历史在 `notifications` 里）。**每一次打出去的请求都记一行，成功与失败都记，也含被限速的那次**
   （宁可高估：账本要回答「打出去多少次」，不是「成功多少次」）。上限窗口与单位不同就如实不同：

   | provider | 单位 | 窗口 | 免费上限 | 限速 |
   |---|---|---|---|---|
   | `polygonscan` | calls | 日 | 10 万 | 5 calls/s |
   | `helius` | credits | 月 | 100 万 | 10 req/s |

   Helius 一次 RPC（不论哪个方法）= 1 credit，因此 `calls` 与 `credits` 同步记 1。

7. **用量 >80% 报警，且只在账本上判定**（`ALERT_RATIO = 0.8`，FR-C6-11）：阈值判定是
   `Usage.over_threshold`，只读数据库，因此可以脱网断言。免费额度内**没有计价**：超额的表现是
   限速/拒绝，不是自动计费，所以成本显示为 ¥0（不编一个假价格）。

8. **限速是「报警」而不是「悄悄重试」**：客户端撞到 HTTP 429 / `Max rate limit reached` /
   JSON-RPC 里的 429 措辞就抛 `RateLimited`，调用方写一条 `chain_rate_limited`（critical）报警。
   「这段时间看不见链上」本身就是必须让人知道的事实 —— 静默退避正是 FR-C6-11 要禁的那种漏检。
   日常限速用**最小间隔限速**（容量 1 的令牌桶等价形式，稳态速率 = 供应商上限）：不打满突发容量
   是有意的，会打满速率的是补扫翻页，那正是需要「慢一点、别撞 429」的地方；不需要等待时不 sleep，
   轮询不会被拖慢。

9. **告警闸门按 `(kind, provider, 额度窗口)` 进程内去重**（`AlertGate`）：阈值与限速每轮都重新
   判定，不去重就会每 60 秒写一条一模一样的通知。**恢复后 `forget`**（某个供应商又通了，或额度
   回落后再越线，要能重新报警）；**重启后重新报一次是有意的** —— 重启本身就是一次「重新看现状」，
   「这件事还在吗」正是运维要的答案。级别写死在 `alerts.SEVERITIES`：三种链上异常（额度越线 /
   限速 / 拉取失败）一律 `critical`，不由调用点临时决定。

10. **端点与凭据**：Polygon 用 Etherscan V2 多链 API（`api.etherscan.io/v2/api?chainid=137`）——
    `api.polygonscan.com/api` 已 301 迁移过去，继续打旧域名会拿到重定向而不是 JSON。Helius 用
    JSON-RPC（`mainnet.helius-rpc.com/?api-key=…`）。API key 只从仓库外 `.env`（0600）读
    （`POLYGONSCAN_API_KEY` / `HELIUS_API_KEY`），**异常消息里只有状态码与供应商原文，绝不含
    key 或带 `apikey` 的 URL**（AC-12）。监听层没有任何签名能力：没有私钥、没有助记词、没有
    派生以外的钱包设施（FR-C6-17..19）。

11. **传输层是可注入的缝**（`Transport` 协议 + `UrllibTransport` 缺省实现）：两个客户端与
    `Watcher` 的账本、时钟、sleep 都可注入，于是「限速 → 报警 → 补扫找回那一笔」这一整条链路
    在**断网**下可验（NFR-GA-4）。stdlib `urllib` 够用，不为此引入新依赖。

12. **翻页有上限，撞上限是「报警」而不是「给半截」**（`MAX_PAGES = 10`，1000 条/页）：翻满上限
    且最后一页仍是满页时，客户端**多探一页**确认到底还有没有剩，有剩就抛 `ProviderError`。
    这一页探询不是洁癖：Polygon 的游标是「原生 + ERC20 两个列表共用的一个区块号」，把半截历史
    当成全部会让另一个列表还没取回的那段被游标越过去 —— 那正是 FR-C6-11 要禁的静默漏检。
    撞上限时 watcher 写 `chain_fetch_failed` 报警且**不推游标**，下轮 / 补扫重来。确实是整倍数
    边界（刚好到底）则由探询结果为空区分开，不误报。

13. **「可查当日/当月成本与额度」的当前出口是 CLI `danmu-intel chain-usage`**：打印每个供应商的
    当日/当月用量、上限、限速、越阈标记、最近一次失败，以及所有监听游标（扫到哪了）。后台页面
    属 T12，届时读同一批函数（`QuotaLedger.usage` / `cursor.rows`），不另建数据源。

## 后果

- ✅ 漏一笔也能找回：限速/失败会让游标停在原处（游标不假装进度），恢复后 `rescan` 按地址查全历史
  重新发现它（AC-5），全程有 `chain_rate_limited` / `chain_fetch_failed` 报警留痕（FR-C6-11）。
- ✅ 额度可见：`chain-usage` 给出当日/当月用量与越阈状态；每次调用（含失败）都入账，账本可用于
  事后核对「那段时间为什么瞎了」。
- ✅ 零资金风险面：代码里没有任何可动用资产的凭据，也没有能签名的东西；key 只从 `.env` 读、
  只进查询参数、不进异常与日志。
- ⚠ **翻页有上限**（`MAX_PAGES = 10`，1000 条/页）：一次扫描最多覆盖 1 万条记录。收款地址的
  真实历史远小于此；真撞上上限时是**响亮的失败**（报警 + 游标不动，见决策 12），不是半截历史。
  届时把 `MAX_PAGES` 调大或改成分段补扫，属于那时的决定。
- ⚠ Polygon 只覆盖原生币与 ERC20（`txlist` + `tokentx`）；其它入账形式（内部交易、ERC721）不
  监听。收款只用 MATIC 与稳定币，够用；将来要收别的东西时新增一个 action，不改形状。
- ⚠ Solana 金额来自节点的余额快照（`pre/postBalances` 与代币余额差额），不是自建代币账户推导：
  同一笔交易里我们既有付出又有收入时以**净额为正**为准（「入账」的正确口径）。
- ⚠ 告警去重只活在**进程内**：同一进程内不刷屏，重启后同类会再报一次（见决策 9）；跨进程去重
  与投递属 T11。
- ⚠ `chain-watch` 目前是前台进程（长驻或 `--once` + cron）。交给 PM2/系统服务托管属运维，
  不在本层代码里（也刻意不引入进程管理依赖）。
