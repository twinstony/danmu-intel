# ADR-0012 报告三形态、事实·解读分层与溯源

## 状态：已接受

## 上下文

需求 FR-C4-2/3/7/9/10、§6.6（十一段固定结构）、§6.9（解读约束）、§7.1（2/10/15 分钟）、
AC-1（事实零错误）、AC-16（缺解读段不得发布）；设计 §10.1–§10.4、§11.2。Ticket #8（T5）
要把「三形态 + 事实·解读分层 + SHA256 溯源」落成可验收的东西。

设计文档没写到接口级、必须在实现时定死的有几处：段性质怎么标、三形态的段集差在哪、
「已完成节点」怎么进正文、`fact_layer_hash` 到底哈希什么（第 10 段本身就是事实段，
直接哈希正文会自指）、版本与页面文件是什么关系、发布时「来源可解析」对什么校验、
LLM 调用点缝在哪。

## 决策

1. **段性质只有两种标记**：`fact` / `interpretation`。§6.6 里「事实 + 解读」的段两种标记
   并存（段 2、7）；「事实（风险提示）」是事实标记 + 限定说明（段 5）。显示用的
   `nature` 由标记派生，`tests/unit/test_report.py` 逐行比对需求文档 §6.6 的表格。
2. **形态决定段集**（同一形态每次发布的段集固定 → NFR-Q-2）：
   - `live_brief`：全十一段**减去段 7「预测验证」**——它要拿最终结果做对照，赛中发布只能
     写出空话；其余十段都能仅凭已完成节点产出。时限 120s。
   - `full` / `review`：全十一段。时限 600s / 900s。
   三形态的段集、触发方式与时限进代码为常量（`report/forms.py`）；设计 §10.2 的逐阶段
   预算表（合计 115s）同样落成常量，实测耗时对着它记账。
   `content_json` 的每段形如 `{no, title, kinds, nature, body, sources}`：`kinds` 是标记
   列表（设计 §10.1 的 `kind` 字段；「事实 + 解读」时两个标记并存），`nature` 是 §6.6
   「内容性质」列的原文。
3. **赛中快报必须显式声明已完成节点**（`--completed-game`）：进行中的那一局既没有完整
   事实，也不该被当成已完成的发；不声明就直接报错，不靠猜。
   **「已完成节点」落在 `ReportScope` → `scope_facts()`**：赛中快报只把已完成小局放进
   `games`，并把弹幕收窄到这些局的时间窗；未完成节点只出现在取材范围那句
   「未纳入本报告的节点：G3（进行中，不发布其段落）」里。这样报告里每个数字都对得上它
   自己声明的覆盖范围（AC-1 的口径）。
4. **`fact_layer_hash` 哈希的是事实层输入，不是渲染后的正文**：比赛信息 + 算法版本 +
   覆盖小局的切片边界与规则统计 + 落盘文件清单 + 覆盖行的行摘要的规范 JSON 的 SHA256。
   第 10 段是事实段且正文里要印这个哈希，哈希正文会自指循环。解读层的输入**只有**事实层：
   `Interpreter.interpret(spec, facts)` 拿不到别的东西。
5. **解读层是注入缝**：`Interpreter` 协议（`state` + `interpret`），缺省 `RuleInterpreter`
   规则直出并把 `llm_state` 如实写成 `rule_fallback`（ADR-0003：降级不静默）。本票不接
   真 LLM；T6 实现同一协议并把 `state` 标成 `llm` 即可，组装与渲染层不用改。
6. **版本与产物分家**：`reports(match_id, kind, version)` 只增不改（FR-C4-9），每行带
   `content_json` / `fact_layer_hash` / `llm_state` / 检查结果 / 实测耗时；页面固定为
   `site/matches/<match_id>/<kind>.html`，被同形态的新版本覆盖。T1 的
   `site/matches/<match_id>.html` 直接删除（AGENTS.md：不留兼容层）。
7. **发布钩子三项阻断性检查**：段集齐备（缺段/空段/多段）、解读段齐备且已标注（AC-16）、
   来源可解析。时限超预算**不阻断**（NFR-T 末句：准确性优先），只记进检查结果。
   拒绝发布时写一行 `state='failed'` 留痕，但不写页面。发布之后由
   `verify-sources` 对着**页面里冻结的哈希**复核（T1 留下的守卫不变）。
8. **「来源可解析」的锚点是采集时封存的 SHA256**（`danmu_segments.sha256`），
   不是组装时现算的区间摘要——现算的摘要永远等于当前文件，等于没查。

## 后果

- ✅ AC-1 / AC-16 可测：事实逐项对着原始记录重算；缺解读段（或用假 LLM 注入未标注的
  解读）时发布被拒绝且不留页面；原始记录被改动后 `report` 与 `verify-sources` 都会拒绝。
- ✅ 三形态时限、段集、性质都在测试里被断言，结构不会随生成方式漂移。
- ✅ T6（真 LLM）与 T7（发布闭环）各自只需接一个缝：`Interpreter` / `releases`。
- ⚠ 「快报不发布段 7」是判断：设计 §10.2 只写了「核心事实段（结果/关键局/关键数据）」，
  需求 §6.10 又写「赛中快报与完整版含全部解读段落」。本实现选择「保留全部解读段、
  去掉唯一依赖终局的段」。若产品要的是更小的快报，改 `report/forms.py` 的
  `LIVE_BRIEF_SEGMENTS` 一处即可（发布检查与测试会跟着走）。
- ⚠ `full` 与 `review` 目前段集相同，差别在时限与（T7 的）可见性；需求 §6.6 的十一段是
  固定的，将来 review 若要单独的「数据修正」内容，只能写进既有段而不能加段号。
- ⚠ 未接灰信号（T4）/盘口数据源时，段 5、8 是纪律声明而不是数据事实，正文里已如实说明。
