# ADR-0019 后台实现：aiohttp + 零前端构建、页面只读与写操作集中、数据源改动走同一个版本号

## 状态：已接受

## 上下文

需求 FR-C8-1..6 / Q-2 / Q-8 / NFR-T-4 / NFR-S-3 / NFR-S-4 / AC-7、设计 §14.1–14.4、
ADR-0007（后台形态：独立进程、仅 tailnet、单管理员、签名 cookie、配置走版本号）
与 ADR-0011（采集监督：一房间一子进程、版本号变了重起子进程）。

设计与需求把「要什么」定得很清楚（12 条页面、只监听 tailnet、单管理员、
所有写操作留痕、配置 1 分钟内生效、凭据不进库），但**没写到实现级**：

- ADR-0007 写的是 **FastAPI + Jinja2**。这两个都不是项目依赖（`pyproject.toml` 只有
  `aiohttp`，公开面 `api.py`、会员 HTTP 边界都在用它），装不装、值不值得装？
- §14.1 的页面清单数下来是 **12 条**，而 issue #22 的标题写「11 页面」——
  哪一个是准的、以谁为准写死在测试里？
- 「配置 1 分钟生效」的版本号只覆盖 `config` 表。**数据源登记表（`rooms`）的增删**
  同样要 1 分钟内对采集生效（FR-C8-1/C8-2、需求 §3.4「添加直播间 → 一分钟内生效，
  无需重启服务」），它落在哪个计数器上？
- 监督进程的房间集合原本由命令行一次性给定，怎么变成「跟着登记表走」？
- 「非 tailnet 请求 403」以什么为判据；`X-Forwarded-For` 能不能信？
- 12 个页面 + 16 个写操作怎么组织，页面只读这件事由谁保证、怎么验？
- 管理员凭据落在哪，会不会顺手把口令写进库或仓库？

## 决策

1. **框架用 `aiohttp`，不引 FastAPI/Jinja2**。形态决策（独立进程、仅 tailnet、
   单管理员、签名 cookie）照 ADR-0007 不变，只把框架细节换掉：项目已有的 `aiohttp`
   起应用 + 中间件，页面用 `admin/html.py` 的极简渲染器服务端直出
   （转义、布局、表格、表单四个原语，与站点产物的渲染同一路子）。于是后台**零前端
   构建链、零新增依赖**（AGENTS.md：先看已有依赖，够用就不加）。
2. **页面清单以设计 §14.1 为准，共 12 条**（概览 / 比赛管理 / 房间与数据源 / 切片复核 /
   灰信号评审 / 报告 / 发布与回滚 / 会员与订单 / 通知与告警 / 配置 / 审计日志 /
   成本与额度）。issue #22 标题的「11」是笔误：它的正文与 AC 列的条目数就是这 12 条，
   AC 明文指向 §14.1。清单**写死在测试里**（路径 + 标题 + 渲染函数），改一边就红。
3. **页面只读，写操作只有一处入口**。`admin/pages.py` 的渲染函数一个写语句都没有
   （测试递归遍历页面渲染过程里的 SQL，出现 `INSERT/UPDATE/DELETE` 即失败）；
   写操作集中在 `admin/actions.py` 的 `ACTIONS`（16 条），每条都调用**已经带审计的
   领域函数**，或自己补一条 `audit_log`（比赛/房间增删改、报告发布、登录/登出）。
   失败一律转成页面上的红条（`?err=` + 人话原因），不静默。
4. **口令与会话**：口令以 PBKDF2-HMAC-SHA256（20 万次迭代、每口令新盐）哈希写进
   仓库外 `.env`（0600，`ADMIN_PASSWORD_HASH`），明文不落盘、不入库；
   **哈希同时是会话签名密钥**——改口令即所有旧会话当场失效，因此不需要第二份秘密。
   cookie 只有「到期时刻 + HMAC 签名」（`v1.<毫秒>.<签名>`，12 小时，HttpOnly +
   SameSite=Lax，经 https 反代时 `--secure-cookie` 加 Secure），登录按 IP 限流
   （1 分钟 10 次）。登录成功/失败/登出都进 `audit_log`。`SameSite=Lax` 同时挡掉了
   跨站发起的 POST（浏览器不会带上 cookie），因此写操作不需要另加一套 CSRF token。
5. **tailnet 判两层，取不到对端 IP 就拒绝**：进程绑定时 `require_tailnet_host` 拒绝
   `0.0.0.0`/公网地址（只肯绑 `100.64/10`、`fd7a:115c:a1e0::/48` 或回环）；每个请求
   再判一次对端 IP，非 tailnet 一律 **403**（连登录页都不给看，AC-7）。
   `X-Forwarded-For` 第一跳优先（`tailscale serve` 在本机代理时会填），
   拿不到合法 IP 时**默认拒绝**而不是默认放行。
6. **「1 分钟内生效」的载体是同一个版本号，不管改动存在哪张表**。
   `config_store.bump(keys=…)` 只递增版本号、不写 `config` 行，供「存在别的表里、
   但同样要跨进程生效」的改动使用；今天只有数据源：`rooms.add_room / update_room /
   delete_room` 各递增一次。监督进程每轮调度读一次版本号，变了就做两件事，
   且**都在一个轮询周期（5 秒 ≪ 60 秒）内**：
   - 对齐房间集合（`registry`）：新登记的房间立刻纳入监督（退避 0），
     被删掉的房间停掉子进程并写明原因（`state='removed'`，不算故障、不计入重启上限）；
   - 按新配置重起还活着的子进程（ADR-0011 决策 4 的既有路径）。

   `supervise --from-registry` 把房间集合指向登记表（而不是命令行参数）；
   配置读取本身仍走进程内 60 秒 TTL 缓存，因此**任何**进程对配置的滞后不超过 60 秒。
7. **后台的发布/回滚与 CLI 是同一条闭环**：`ActionContext.release()` 注入
   发布上下文（生产 = 真 git + Vercel；测试 = 本地模式 `--no-deploy`），
   按钮与命令行走同一套检查、原子替换与回滚代码。

## 后果

- ✅ AC-7 两半都可测：非 tailnet 请求 403（含登录页与报告预览）、非管理员无 cookie 403；
  配置保存即递增版本号 + 本进程立即生效，跨进程 ≤60 秒由「版本号 + TTL 缓存 + 子进程
  重起」三件事分别断言。
- ✅ FR-C8-1/C8-2 的「加直播间 1 分钟内生效」落在同一条版本号链路上：后台登记 →
  `rooms` 写入 + 版本号++ → 监督进程对齐房间集合 → 新房间的子进程被拉起。
- ✅ FR-C8-4 可断言：16 个写操作 + 登录/登出都在 `ACTIONS`/审计里，
  端到端一遍走完能从 `audit_log` 里数出来。
- ✅ NFR-S-4 三件套齐备：`tools/check_no_secrets.py`（含 `xprv` 模式）、
  `deploy/hooks/pre-commit`（`deploy/hooks/install.sh` 装进 hooks 目录）、
  以及「塞假私钥必须被抓到」的测试用例 + 「跑完一整轮后台，库里搜不到口令明文与哈希」。
- ⚠ `X-Forwarded-For` 本身可伪造，但服务只绑 tailnet：能连上的人本来就在 tailnet 内，
  因此伪造它换不来额外权限。若将来经公网反代暴露，这条判据必须重做。
- ⚠ `config_version` 的语义从「配置版本」扩成「跨进程生效信号」（`keys_json` 里写明
  是哪个域，今天会出现 `rooms`）。将来若有第三类表要热生效，**同样走 `bump`**，
  不要另起一套变更通知机制。
- ⚠ 只有管理员一类角色（需求 Q-8），没有多角色与权限矩阵；口令轮换会踢掉所有在线会话
  （刻意的：哈希即签名密钥）。
- ⚠ 后台进程自身没有心跳（与 ADR-0011 对监督进程的说明相同），挂了靠 systemd/PM2
  的 `Restart=always` 兜底；绑定前的地址检查与启动时的口令读取失败都会**拒绝启动**
  而不是带默认口令起来。
